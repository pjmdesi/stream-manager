- **STR-16** [differentiator]
  Detect and warn about unfinalized (crash-orphaned) video files, and offer the one-click repair. Filed 2026-09-02 after a real Hybrid MP4 crash test: the footage survives but the seek index was never written, so players treat the file like a stream (no end time, no seeking, artifacts). SM's Lossless Copy preset already IS the repair; this feature closes the loop: detect, explain, one click to fix.
  - Detection is a cheap structural check, not a decode: MP4 is unfinalized when it has no complete moov atom (fragments without an index); MKV when it lacks its Cues/duration elements (the classic crashed-OBS-MKV signature). A header walk with seeks over payloads, milliseconds even on multi-GB files.
  - Wrinkle 1: an IN-PROGRESS recording is byte-identical to a crashed one. Only flag when unfinalized AND quiescent (no growth or mtime change for several minutes). The player already special-cases in-progress OBS files probing duration 0; reuse that awareness.
  - Wrinkle 2: cloud gating. Never probe an offloaded placeholder (probing hydrates it); check local files only and cache the verdict in the item metadata so the scan does not repeat.
  - Surfaces: a warning badge on the file card in the files grid with a tooltip explaining what happened (recording was interrupted before finalizing; data intact, index missing); the same indicator rolled up in the stream list's video-count column popup so it is visible without opening the item; an honest banner if such a file is opened in the player.
  - One-click repair: clicking the warning adds the file to the converter with the Lossless Copy preset pre-selected. Output is a new file; the original stays until the user verifies, per the usual ethos.
  - Copy: extend the Lossless Copy preset's description (and possibly name) to include repair as one of its functions, in the preset UI and the Help modal's converter entry (currently framed only as container compatibility / OBS Remux Recordings equivalent).

- **STR-17** [perf]
  Stream item rows render their thumbnails as full-size images (usually 1280x720) scaled down by CSS to the thumbnail column width (85-170px), so Chromium keeps re-interpolating a large bitmap, including during the row hover zoom animation. Likely a contributor to slowness and hitching while the streams page is open. Reuse the canvas downscaler that already serves the recents rows on the player and thumbnail overview pages (SmoothThumb in RecentRow.tsx): resample once into a canvas at the max display size of the thumbnail column times devicePixelRatio so the compositor works with a small texture from then on.   2026-09-06: attempted as a v2.6.0 ride-along, shipped, and reverted the same day. The swap itself worked (a downscale mode on ThumbImage rendering through SmoothThumb, with debounced resize redraws) and the animation gain was marginal at best, but it introduced a worse problem: on app start the thumbnail column sat blank for a few seconds, because 200+ rows each decode the full image and run the resample chain on the main thread before anything paints, where the old img tags painted progressively from cache. A future pass must make the resample non-blocking: paint the raw img immediately and swap in the resampled canvas when it is ready, stagger the work over idle time (or only for rows near the viewport, which pairs with STR-4), or persist resampled versions to disk. The reverted implementation is in git history (the STR-17 commit and its revert). Also save the resampled images to the cache, replaced when updated, and loaded from cache when they are needed.

- **STR-23** [bug] [done]
  A stream delete in a `_DEV` dist (2026-09-12, while testing STR-21) triggered hydration of a large number of cloud files and the app became unresponsive until it was ended from Task Manager. Reproduced three more times the same day, always in a dist build (a dev-server run of the identical steps did not hydrate), by creating an empty stream item and deleting it, and once right after an SM offload of the same stream (the 2025-11-28 folder, which has nested asset sub-folders).
  Procmon findings 2026-09-12 (capture: app launched 6:48:47 PM, test stream created 6:48:59, deleted 6:49:04, hydration began 6:49:08). What the app does: `streams:deleteFolder` pauses the chokidar watcher (`pauseDirWatcher` closes it) and restarts it afterwards (`startDirWatcher`, `chokidar.watch` at depth 6). Rebuilding the watcher makes chokidar 3 register an `fs.watch` per file, and on Windows each registration opens the file with read-data access (lstat, then CreateFile "Read Data, Read Attributes, Synchronize", GetFileInformationByHandle, two FindFirstFile lookups, close). That is 2,168 file opens across the library, once at startup and again after every restart. The same pause-and-restart wraps reschedule, converter output writes, and every cloud offload (`ensureOffloadPaused` in cloudSync), which is why a hydration was also seen right after an SM offload. Causality: the first hydrated file (a PNG in 2025-11-28) was opened by the app at 6:49:08.4517; explorer.exe opened it by file ID at .4531, the Synology daemon touched it at .4537, and cloud-drive-ui.exe read its data from .5580. Hydration then followed the app's walk order through the folder. The app itself read no data from any of those files. Only preview-able types hydrated (png, jpg, gif, pdf, docx, zip); the mkv, mp4, and wav files opened by the same walk did not, so the download is the Synology client generating previews in reaction to the opens rather than anything reading the files. Cleared: the recycle-bin move (only empty test folders were deleted), the STR-2 size walk (stat only, and a stat on a placeholder does not hydrate), the out-of-sync thumbnail hash (primaries are pinned and local; the placeholder gate added in the first attempt stays as a harmless defensive change), image loads from any page (none happened), and Explorer thumbnails on their own.
  Per-file causality (dist capture): for each of six files spread over eight seconds, the Synology daemon first touched the file 2 to 6 ms after the watcher's open of that exact file, and Explorer within 25 ms. The libuv side is real but not sufficient on its own: libuv 1.46 (Electron 34) never opened the watched file, libuv 1.52 (Electron 44, Node 24) opens it with FILE_LIST_DIRECTORY access (the FILE_READ_DATA bit) and queries it by handle, so since APP-1 every `fs.watch(file)` is a data-access open. A Procmon capture of the dev server doing the identical create and delete showed the identical 2,440-file walk with identical flags and NO reaction from the daemon or Explorer, so the reaction depends on the process, not on the syscalls. What the reaction is: Windows treats the opens as app-initiated background downloads (Explorer raised the "app is downloading" toast three seconds into the burst and looked up the app's exe for it; the toast handler's counters show 41 such toasts with 33 user interactions), and the Synology client generates thumbnails for every preview-able file it is told about and uploads them to the NAS (its UI process reads the files, writes them to its thumbs cache, and its ui.log shows the uploads), which is the hydration. That is the type split: the 92 hydrated files are every png, jpg, gif, pdf, docx, and zip under the folder; the mkv, mp4, wav, mp3, md, and af files were placeholders too, were opened by the same walk, and got icons instead. Windows gates app-initiated downloads per application (Settings, Privacy and security, Automatic file downloads, where an app blocked from a toast is listed); the dev electron.exe being blocked there and the dist exe not is the leading explanation for dev versus dist, pending a look at that page. Probe runs of the same `fs.watch` outside the app were inconsistent (none of four variants hydrated before a reboot, three of four after it), so probes are not a reliable oracle here. After the reboot the dist's startup walk hydrated one video per launch (2024-04-28 first, 2024-05-03 next) with the app frozen for the whole download, which is the original hang; the per-launch selection is unexplained. Cleared: Explorer window state, Malwarebytes (attribute checks only), shell thumbnails from the app (dead code), the sync client's own event handling (dev runs produced the same sync events).
  Fix direction: stop opening files in order to watch them. - **PLR-4**
  Detect empty (silent) audio tracks for the player's multi-track feature, so the track picker can flag tracks with no audio before the user extracts them. My OBS recordings always mux every configured audio channel, but several are use-case-specific channels that usually stay unused, so they exist in the file as full-length encoded silence. ffprobe metadata can't reveal this (a silent track looks identical: same duration, channel count, packets throughout), and sampling a few points won't work either, since a track might carry one brief but important sound (e.g. a single subscribe alert lasting a few seconds in a 4-hour stream) that any partial scan would miss. So detection has to cover the whole track. Two-tier approach: (1) Primary, cheap pre-check, no decode: scan compressed packet sizes across the entire track via `ffprobe -show_entries packet=stream_index,size` (one pass classifies every audio track at once). Encoded digital silence compresses to almost nothing (which is exactly why empty tracks already extract ~3x faster), while real audio, including a one-time loud alert, shows up as a spike in the per-packet sizes. Key: threshold on the MAX (or a high percentile) packet size, NOT the average/total, because a 3-second sound averaged over hours would otherwise be invisible. Caveat: it's a heuristic, defeated by a CBR encoder that pads every frame to a constant size regardless of content, but the observed 3x extraction speedup is direct evidence this OBS encoder doesn't pad, so silence is genuinely lighter in these files. (2) Certainty upgrade, piggybacked on a decode we're already doing: when a track does get extracted, run `volumedetect`/`astats` during that same decode (`max_volume` of about -91 dB / -inf means silence) and overwrite the heuristic verdict in the cache. Cache the per-file+track result mirroring the existing audioCacheManager pattern, surface an "empty / no audio" badge in the multi-track picker so empties can be skipped at a glance, and keep the flag ADVISORY (still allow a manual extract) so a heuristic miss can never hide real audio. Fits next to `probeFile` in `ffmpegService` as a `probeTrackLevels` plus a small cache and IPC, without touching the extraction path.

- **CONV-12** [bug] [done]
  A converter job whose cloud download is cancelled outside SM (through Windows or the sync client) stays on "Downloading from cloud" forever instead of failing, and pausing and resuming the sync client never restarts the download. Cause: the converter's hydrate wait (ensureHydrated for archive groups, the inline wait in startConversionJob for standalone jobs) nudges the file with a single one-byte read and then polls file attributes every two seconds. Attributes cannot distinguish a cancelled recall from a slow one, the nudge's own error result is discarded, nothing re-issues it, and the archive-group path has no timeout at all (the standalone path has six hours). The cloud widget's downloads use CfHydratePlaceholder (hydrateOnePath in cfapi.ts), which blocks until the recall ends and returns an error code on failure. Fix: move the converter's wait onto that same call so both paths share one implementation and a dead download becomes a job error with a readable reason; SM's own Cancel keeps working because the abort-by-dehydrate makes the blocking call return, and the cancelled flag is checked before treating that as a failure (as the widget's worker does). Verified 2026-09-11 with the widget: pausing the sync client fails the in-flight files (the API returns an error), files requested while it is paused sit on "working" and complete normally once it is unpaused (the request is held by the OS, which is correct), and a cancel from the Windows notification does NOT make the row fail (the request stays pending, and the same resume completes it). So the shared call fixes the hang on provider-side aborts and gives the archive path an end state, but a Windows-side cancel is indistinguishable from a paused provider on both paths. Handle that with visibility rather than guessing: show how long the row has been waiting once it passes a few minutes with no completion, with a hint that the sync client may be paused or the download cancelled, and leave Cancel (and Requeue) as the user's exit.
  Built 2026-09-11, awaiting review. New shared wait in `services/cloudHydrateWait.ts`, used by both converter hydrate paths (the old touch-and-poll is gone). It keeps a live CfHydratePlaceholder request in a child process (`startHydrateRequest` in cfapi.ts) as the ear for provider errors, polls attributes for completion, and re-issues a fresh request every 5 minutes as the restart nudge for a download cancelled from Windows (rolling window of two live requests per file, since dropping a request does not touch the transfer). A provider error (pausing the sync client aborts in-flight transfers, a stopped client rejects requests) fails the job at once with the provider's reason; archive-group failures go through the same error path as encode failures (red row, group hook short-circuited, siblings continue). ### Music Manager

- **BIG-1** [needs-design] [differentiator]
  Music Manager, phase 1: a music library and player for stream background music (interstitials, lulls in a game), replacing the OBS media source + Tuna plugin setup. Architecture decided 2026-09-02:
    a. SM plays audio THROUGH an OBS browser source: SM serves a page from a loopback-only local HTTP server (no firewall prompt) containing the actual audio player; OBS loads it once and the music joins the OBS mixer like any other source. Likely split into a persistent hidden audio source plus a separate visual now-playing overlay source so the card can be scene-specific while music keeps playing. Track data and artwork push over a WebSocket, so metadata shows instantly and paused actually looks paused (the two big Tuna gripes). No helper placeholder files.
    b. Library: a separate music root folder (a new concept, not stream items; no seasons, no cloud offload pressure). Read the real tags (title, artist, album, embedded art) so mismatched filenames stop mattering; browse, search, and sort by metadata; file ops in-app.
    c. Playlists as first-class objects: group tracks into sets per stream type or mood, and switch the active playlist from SM without touching the OBS source. Shuffle within a playlist.
    d. Player controls always exposed in SM (play/pause, previous, next, seek, volume) plus one clean fixed overlay layout for v1: art, title, artist, progress, correct paused state.
  Chromium plays mp3/aac/flac/ogg natively, so no transcoding is involved. Follow-up phases are the MUS items below, all blocked on this one.

  2026-09-02 triage notes (kept as a big maybe; no near-term plans):
  - Per-format reality flips the original assumptions: PSD is the EASIEST target, not the hardest. The spec is public, layer-level structure has been stable for decades, and an actively maintained JS library (ag-psd, MIT) reads the layer tree, text layers with fonts/sizes/colors, positions, embedded images, and some effects. Affinity's native formats are proprietary and unparseable, but Affinity exports PSD, so it is covered for free. Canva has NO native file export at all (only rendered PNG/JPG/PDF, plus SVG on some plans), so a "Canva import" can only ever mean its PDF or SVG export. Native .ai is ruled out; the PDF-compatible route is a real PDF but vector-PDF-to-layers is its own project and thumbnails are rarely made in Illustrator.
  - Scope reframe 1: build ONE importer (PSD as the universal interchange target), with SVG as a possible later add (maps to layers cleanly and catches Canva and Figma-style exports).
  - Scope reframe 2: promise a STRUCTURAL import, not a pixel-perfect one. Bring in text content, font names, approximate size/color/position, and images as assets; the user re-styles with SM's own effects. Report per-layer what was rasterized or skipped (honest-errors ethos), and the existing missing-font protection applies on import.
  - Possible phase 0, could split into its own ticket someday: import the flat rendered image (every tool exports PNG) as a locked background layer and rebuild just the text on top with SM layers and templates. Most of the migration value, works for every tool, needs no parser.
  - Sizing policy (canvas is locked to 1280x720): same aspect ratio at any resolution rescales uniformly and silently (a 2/3 scale of a 1920x1080 source is pixel-equivalent; note it in the import summary). Different aspect ratio asks in the import dialog: Fill (uniform scale to cover, centered, edges overhang but stay editable; the default), Fit (all visible, empty margins), or As-is (100% scale for cherry-picking pieces). Scaling is always uniform, never stretch, and applies to the whole look: positions, sizes, font sizes, AND effect parameters (shadow offsets, blur radii, stroke widths), or the import arrives with wrong-weight effects. Upscaling from smaller sources is allowed but flagged honestly (raster layers may be soft; text re-renders crisp).
  - Long-term maintenance outlook: low, for structural reasons. PSD is append-only in practice (new Photoshop features arrive as new tagged blocks that old readers skip by design), the structural-import promise means unmapped new features are documented behavior rather than regressions, and there is always a graceful floor (PSDs embed a flattened composite and per-layer rendered pixels, so anything unparseable degrades to an image layer or the flat background). A pinned ag-psd stays useful even if abandoned, since a frozen format does not rot under it. Detection plan (SM has no telemetry, so detection is deliberate): the per-layer import report doubles as the signal with a "Copy report" button for pasting into GitHub issues; a small PSD fixture corpus in CI with snapshot tests of the imported JSON (include Affinity- and Photopea-exported PSDs, since PSD really means everyone's dialect) gates ag-psd bumps; one saved sample file per major Photoshop release run through the importer as a ten-minute canary ritual; and watching ag-psd's GitHub releases for new-block support worth a bump.
  - Photoshop artboards are not pages: they are special layer groups carrying a frame rectangle, all sharing one document coordinate space. Handling: one artboard (or none) means its rect (or the document bounds) is the source canvas; multiple artboards get a picker at import, with layer coordinates re-based to the chosen artboard's origin, plus an "import each artboard as a variant" option (thumbnail variants already exist and a multi-artboard thumbnail PSD is probably a variant set). Floating layers outside every artboard are skipped and listed in the import report. PDF pages, if that route ever happens, are true pages and reuse the same picker; SVG is single-canvas.
  - When built, add a Thumbnails section entry to the Help modal: what the importer brings in, what gets flattened or skipped, and what the import report means.
